# Zotero-OpenReader — engineering log, 2026-10-18

## A provider enabled by hand stayed "held off" by the settings sync (2026-10-18 00:02, issue #192)

The `held` record in `webdav.syncState` was deleted only where the
transport's own post-adoption check passed, and that check runs only for
a section the sync just adopted something in. The pane's Enable, which
runs its own check before it sets `<id>.enabled`, reached the transport
only as a pref change to stamp, so the Sync group's line went on saying
"stays off on this computer" — across restarts, since `stats().held` is
read from the stored state — while the provider worked. `changed()` now
deletes the record when a held provider's `.enabled` turns true; it never
runs for the sync's own silent writes (`applying`), so only the user's
Enable or a restore reaches it, and a restore runs its own check after.
The line redraws at the next completed sync, which the Enable arms after
the quiet period.

## A settings change right after an adoption from a faster clock was reverted (2026-10-18 00:05, issue #205)

An adopted item's stamp is stored as this computer's own (`stamps[key] =
item.ts`), so after adopting from a computer whose clock runs ahead this
computer holds a stamp in its own future, and `changed()` stamped the next
local change with the plain clock — lower — so the next sync adopted the
file's older value back over it and counted it as "applied here". The
stamp is now `max(now, previous + 1)`, the rule Document voices
(`document-voices.ts`), the positions and `docs/spec/SYNC-FORMAT.md` 6.6
already follow. Storing this computer's clock at adoption instead was
rejected: the adopted key would then read as newer here and be pushed
straight back with this computer as its writer.

## The sync line and the restore report named providers by switch id (2026-10-18 00:10, issue #193)

`settingsStatusText` put each key of the held record straight into
`ztts-sync-status-held` as `$provider`, and `verifyEnabled` joined the
raw ids of the switches it turned off into `$named`. The ids read as
names while the switches were `azure` and `local`; #111–#113 added
`openai-official`, `mimo`, `compatible`, `fishspeech`, `zotero-standard`
and `zotero-premium`, which no other text in the interface shows.
`switchLabel(id, naming)` in `read-aloud/voice-catalog.ts` now names a
switch as the Player names its entry — `providerTierLabel` for a
provider, the local engine's `voiceName` ("Kokoro") through
`providerNaming`, `zoteroTierLabel` for Zotero's two tiers — and hands an
unknown id back as it is (a held record another version wrote). The pane
passes the naming to the sync line through `SyncStatusDeps.settings.naming`;
the restore report reads it from the prefs it already holds. The section
headings ("Cloudflare Workers AI", "Kokoro FastAPI") were the other
candidate; the Player's names won because the other plugin messages
(`memory-sync.ts` `ztts-document-voice-key`) already use them.

## `diagnostics.sharedSettings()` printed the old preset memory in the clear (2026-10-18 00:11, issue #203)

The helper hides a value when its key matches one regex, and #113
dropped `presetValues` from it when the key left the settings. The item
did not leave the shared file: `convertLegacyItems` reads the old
`openai.*` items through and keeps them for the copies still on that
version, and `openai.presetValues` holds each remembered server's
`apiKey` and `headers`. `presetValues` is back in the regex. General
lesson: a mask over a shared file has to cover what the file can still
hold, not only what this version's settings hold.

## macOS 27 lists some voices twice (2026-10-18 01:08, issue #185)

`NSSpeechSynthesizer.availableVoices` on macOS 27.0.1 (build 26A434)
returns 235 entries for 193 identifiers: 42 repeated, each repeat right
after its first and identical in name, language and locale; `say -v '?'`
prints the repeats too, so they come from the system and not from the
JXA script. 26.6.2 printed 191 with none. The "191 for 191" premise of
`mac.ts` held only before 27. Every consumer downstream keyed rows by id
and none could tell two apart: Zotero's `parseVoicesResponse` and
`loadVoices` do not drop a repeat, the next-voice step finds the first
row and lands on its twin, and the voice browser's `playButtons` map
kept the second row's button. `parseMacVoices` now keeps the first record
of an identifier, and `collectCatalog` keeps the first voice of an id in
every provider's entry, the one place both the published list and the
voice browser pass through. By id only: `Aman` and `Aman.premium` share a
label and are two voices (2026-09-06). Not checked: whether Gecko's own
`speechSynthesis.getVoices()` repeats them as well.

## The voice browser kept samples across a Model change (2026-10-18 01:09, issue #190)

The samples map lives as long as the pane and was keyed by voice and
text, so Disable → another Model → Enable, with the window open, replayed
the old Model's audio from it without a request. The reading cache never
had the problem: its key carries `cacheVersion()`, the plugin version
plus the settings that change a voice's audio. Those settings are now
`audioSetup()` in `core/settings.ts`, the same fields in the same order
(the reading cache's key keeps its value), and the voice browser puts it
in front of each sample's key, read at every ▶. Zotero's own samples keep
their key. Seen while moving it: `fishspeech.baseURL` is not one of the
fields, so after pointing Fish Speech at another server the reading cache
could serve a reference id's audio from the old server; not changed here.

## The Windows speech daemon's stop() let a queued request start a new helper (2026-10-18 01:10, issue #191)

`stop()` killed the helper and swapped the `queue` variable, but the
exchanges already chained onto the old tail kept running: the one in
flight rejected, and the next ran `ensureProcess()`, found no process and
spawned one, which nothing held after `src/index.ts` dropped the daemon.
A stop during the spawn or the handshake did the same through `process =
started` landing on a stopped daemon. The Engine cannot cancel these
requests, since the System provider's `speak()` takes no signal. The
daemon now counts generations: `stop()` advances it, a request remembers
the one it was sent in, and one from an older generation rejects before
`ensureProcess()`, or kills the helper it was starting. A send after
`stop()` starts a helper as before. Covered by unit tests against the
fake process only: the Windows machine was not reachable from this
session.

## Verified live on 1.16.12-beta3: System voices once each, samples made again (2026-10-18 02:05, issues #185, #190, #191)

`zotero-tester` ran items 1.17 and 2.11 on macOS 27.0.1 (build 26A434),
all PASS; 1.18 is Windows only and was not run. The build was proved by
the bundle (`sampleSetup` and the helper's stop message). The System
listing, the Player's `_allVoices` and the voice browser's column all
read 193 with no id twice, and the listing logged `macOS lists 193
voices` where it had been 235. Two expected outputs were wrong and were
corrected from the table. During a session a voice key parks its pick in
the Handoff, so the three steps show in the pending target and
`selectedVoiceID` follows at Play; an idle manager with the session ended
could not be reached. And every `diagnostics.systemProvider()` read
spends one `osascript` listing that shows up in the next read's
`spawned`, so a delta between two reads is one too high. Also seen and
left alone: `diagnostics.voiceSwitch()` reports the per-reader `selected`
as null (it reads through an Xray), and Disable on the provider of the
default voice clears the default while the settings window is open.
