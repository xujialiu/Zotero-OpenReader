## A provider enabled by hand stayed "held off" by the settings sync (2026-10-18 00:02, issue #192)

The `held` record in `webdav.syncState` was deleted only where the
transport's own post-adoption check passed, and that check runs only for
a section the sync just adopted something in. The pane's Enable, which
runs its own check before it sets `<id>.enabled`, reached the transport
only as a pref change to stamp, so the Sync group's line went on saying
"stays off on this computer" — across restarts, since `stats().held` is
read from the stored state — while the provider worked. `changed()` now
deletes the record when a held provider's `.enabled` turns true; it never
runs for the sync's own silent writes (`applying`), so only the user's
Enable or a restore reaches it, and a restore runs its own check after.
The line redraws at the next completed sync, which the Enable arms after
the quiet period.

## A settings change right after an adoption from a faster clock was reverted (2026-10-18 00:05, issue #205)

An adopted item's stamp is stored as this computer's own (`stamps[key] =
item.ts`), so after adopting from a computer whose clock runs ahead this
computer holds a stamp in its own future, and `changed()` stamped the next
local change with the plain clock — lower — so the next sync adopted the
file's older value back over it and counted it as "applied here". The
stamp is now `max(now, previous + 1)`, the rule Document voices
(`document-voices.ts`), the positions and `docs/spec/SYNC-FORMAT.md` 6.6
already follow. Storing this computer's clock at adoption instead was
rejected: the adopted key would then read as newer here and be pushed
straight back with this computer as its writer.

## The Windows speech daemon's stop() let a queued request start a new helper (2026-10-18 01:10, issue #191)

`stop()` killed the helper and swapped the `queue` variable, but the
exchanges already chained onto the old tail kept running: the one in
flight rejected, and the next ran `ensureProcess()`, found no process and
spawned one, which nothing held after `src/index.ts` dropped the daemon.
A stop during the spawn or the handshake did the same through `process =
started` landing on a stopped daemon. The Engine cannot cancel these
requests, since the System provider's `speak()` takes no signal. The
daemon now counts generations: `stop()` advances it, a request remembers
the one it was sent in, and one from an older generation rejects before
`ensureProcess()`, or kills the helper it was starting. A send after
`stop()` starts a helper as before. Covered by unit tests against the
fake process only: the Windows machine was not reachable from this
session.

## A duplicate reader supplied another reader's pause and sentence (2026-10-18 02:37, issue #206)

The position sampler observed one reader at a time but kept `speaking`,
`lastSeen`, and the permission to capture a deactivated session under the
attachment's `lib/key`. A duplicate therefore compared its old sentence
with the speaking reader's latest one and overwrote it, while an idle
reader reset the speaking flag on every pass. The next pass announced a
pause again. The saved row's monotonic stamp made that false change beat
an adopted remote position too. This happened before either transport:
changing the merge or delaying sync would only hide parts of it.

Observations now belong to reader handles. Each pass observes all readers
before choosing at most one writer per attachment; a speaking reader wins
even when its sentence has not changed. The losing reader's observation
is still updated, so it cannot take over merely because its sibling closes.
A real paused skip or a new speaking transition remains a local change.
A newly seen paused reader only seeds an empty entry; it does not replace
an existing position with its initial snapshot. Persisted entries and
permanent-deletion guards remain attachment-keyed, and neither positions
file changes its shape.

The close path freezes the individual handle in a WeakSet, not the shared
attachment. This matters twice: a surviving duplicate must still record,
and the late uninit backstop must not revive the captured reader after it
left the list. The old reopening unit fixture reused one reader object;
it now supplies a new handle, as a reopened tab does. Shutdown uses the
same once-per-attachment selection as a normal pass. A paused close checks
for a speaking sibling without consuming that sibling's observation.

Verification before live testing: the original three-symptom reproduction
and its controls pass. The four focused test files pass all 78 tests.
Loading the pristine sampler from 6770786 into those same tests produces
23 failures and 55 passes, including both whole-startup tests: an idle
duplicate must cause no repeated WebDAV requests, while a real pause must
request each of the two files once. The pristine file's Git blob hash was
checked before this differential run. Native close/adoption and EPUB shared
captures both have multi-reader regressions. The live cases are 6.11–6.15;
no real folder or reading position was used in the deterministic tests.

## A group library is numbered per computer, so its positions never met (2026-10-18 11:00, issues #187, #207)

`zotero-tts-positions.json` names an attachment by `{lib, key}`, and
`lib` is the writer's local `libraryID`. Zotero numbers a library when an
install first creates it (`id.js` `_getNext`, `MAX(id) + 1`; a group
known to the sync is created in the order of the server's group-versions
keys, `syncRunner.js` 477-505, 625-645 in 11.0-beta.1), and a feed takes
a number from the same sequence. So a group can be 2 on one computer and
3 on another, and the transport adopted an entry only when
`Zotero.Libraries.exists(lib)` and `getIDFromLibraryAndKey(lib, key)`
held here. The entry stayed in the file, the other computer's own reading
went up under its own number, and the two never met. A pull that adopted
under the file's number would not have helped either: the sampler and the
resume lookup are keyed `lib/key` with this computer's number, so the
adopted entry has to carry the local number. Both halves were measured at
the transport seam before the fix: a key-only adoption check took the
entry (`adopted` 1) and `entryOf(3, K)` was still null; translating the
library first made it resume.

The fix leaves the file's format alone (version 1, four fields: the
1.x serializer strips any added field, and the file retires in 2.0, #128).
`entryHere` in `position-transport.ts` keeps an exact match as it was and
otherwise looks for the key in this computer's user and group libraries
(`Zotero.Libraries.getAll()` walked by index, `libraryType` `user` or
`group`). One library holding it is the attachment; several are refused.
The libraries are read once per sync and once per import. Item keys are
random 8-character strings from a 32-character alphabet, so two documents
sharing one across a user's libraries is not a case worth guessing on.
The adopted copy goes up under the local number with the writer's `ts`,
so the file holds one entry per numbering and settles after one round:
adopt takes only a strictly newer `ts`, and a mirror carries the same
one. `transport.remapped` in `diagnostics.positionSync()` counts the
entries taken under another number, and the debug line says
`(N under this computer's library number)`.

Left as it was: a tombstone (#51) still matches by `lib/key`, so this
computer's deletion does not drop the other numbering's entry from the
file; that computer drops it when Zotero's own sync tells it of the
deletion. The owner's macOS profile has My Library only (measured
2026-10-18), so the live check remaps into library 1 from a number that
does not exist here; two numberings of one real group need two profiles.

Issue #207, fixed in the same branch: the pane's positions line read only
the plugin's own transport, and the Positions File transport had no
`onSynced`. `positionsStatusText` now takes the Positions File's outcome
too and reports a failure of either file, the plugin's own first, each
with its own time and `String(e)` (`SharedPositionsFileError: The
positions file on the server is version 2; …`). Both transports call one
`notifyPositionSync`. Which of the two listeners redraws an open pane
first is a race on the replies, so the whole-startup test holds the
Positions File's reply a second to make its listener the one that must
draw the failure.

## Snapshots and Reading Mode left M to Zotero's lock (2026-10-18 17:12, issue #188)

The DOM follower (`read-aloud/dom-follow.ts`) attached only to views with
an EPUB `flowMode`, so a web snapshot and Reading Mode kept Zotero's own
`ReadAloud` helper lock, which re-locks at every session start
(`setState`, `state.active && !previousState?.active`, reader.js 53364-53366
in 11.0) and at a Resume with the segment on screen (53377-53383). The
plugin's Shift+R native branch also ran `setPositionLocked(false)` in the
microtask window where `forgetViewReadAloudState` had nulled the helper's
state, and `setPositionLocked` acts only `if (this.state?.active)`
(53430-53433), so the unlock was a no-op and the queued push re-locked.

All three views are `DOMView`s with the same helper and scroll their own
iframe window (`SnapshotView.navigateToSelector` 60712-60736,
`SDTView.navigateToSelector` 70404-70423), so the follower now takes every
view carrying `_readAloud` and an `iframeDocument`, places a view without
`flowMode` as a scrolled EPUB, and reports `kind` `epub` / `snapshot` /
`reading-mode` in `diagnostics.autoScroll()`.

Reading Mode in 11.0 is not `_primaryView`: `_setReadingMode` (87943-87990)
makes `_primarySDTView` / `_secondarySDTView` over the PDF view, whose
iframe it hides (`visibility: hidden`), and `_lastView` returns the SDT
view while it is on (`_getActiveView`, 87545-87556). `_views` lists all
four (87569) and `_pushReadAloudToViews` (88113) pushes to each. Since the
SDT view appears after the Player's open, the follower shadows the
internal reader's `_pushReadAloudToViews` once per reader and attaches any
new view before the push reaches it. The PDF follower keeps the hidden
base view; its placements there are not seen.

A web page saved with its own scrolling element (the root does not
scroll) would get nothing from `win.scrollTo`; there the follower calls
the view's `navigateToSelector` (`scrollIntoView`, which reaches nested
scrollers) with `block: 'center'`, `last.reason: 'element'`.

## A pick after an error or the end waited two minutes for nothing (2026-10-18 17:12, issue #194)

Read Aloud's manager sets its own `_paused` on `Error` and `Complete`
(read-aloud-manager-10.0.3.js 845-853) and writes nothing to the
controller, so the Engine's `session.paused` stays false, as the copied
controller has it. The Handoff read `session.paused` as "the reading waits
for Play", took the stopped reading for a playing one, never sent `ready`
and never extended its 120 s deadline. `EngineSession` now keeps a private
`halted` set where it emits `Error` and `Complete` and cleared at the next
`speakInternal` (and at `reset`/`end`); `waitsForPlay` = `paused || halted`
is what the Handoff reads wherever it read `paused`.
`session.paused` itself is unchanged.

## OpenAI-compatible and Azure replies read as what they are (2026-10-18 17:12, issues #198, #199, #200, #201, #202)

- *HTTP errors on the voice list (#198).* `listVoices` of
  `openai-compatible.ts` fell back to the documented voices on any non-OK
  status but 401/403. A gateway's 502/530 for a sleeping server then
  listed OpenAI's eleven voices and called the Document voice
  unavailable. It now falls back only on 404, 405 and 501 and throws
  `statusError` otherwise, which the catalog reports as unreachable. A 200
  with an unusable body still falls back (pinned by an existing test).
- *A login page as audio (#199).* A gateway that wants a browser login
  redirects, `fetch` follows, and the speech route took the 200 HTML page
  as audio, so Test connection said "Synthesis works". The speech route
  now refuses a `text/*` type or one naming html, json or xml; no type,
  `audio/*` and `application/octet-stream` pass.
- *Over 4,096 characters (#201).* OpenAI answers a longer `input` with 400
  `string_above_max_length`; Zotero keeps a sentence of up to 5,000 UTF-8
  bytes as one Segment. The speech route splits such a text with
  Speechify's splitter (moved to `providers/split-text.ts`), asks for the
  pieces at once and joins the MP3 replies. Each piece loses its ID3v2 tag
  and its `Xing`/`Info` frame first: that frame states the frame count of
  its own file, which a demuxer may take as the end of the joined stream.
  The frame length is computed from the Layer III header (144000 or 72000
  × bitrate / rate + padding); the tag sits after the side information
  (MPEG-1 32/17 bytes, MPEG-2 17/9, stereo/mono, +2 with CRC). Whether
  Gecko would have stopped at the first piece without the strip was not
  measured.
- *Azure's voice list (#200)* threw `unknown` for every non-2xx, so a
  refused key read as an outage. 401 and 403 are now `auth`, 429
  `rate-limit`. 403 as `auth` follows the other providers; Azure's list
  was only seen answering 401.
- *A key with a stray space (#202).* `fetch` strips a header value's
  surrounding spaces, so Test connection passed; the WebSocket URL carried
  `%20`. `createAzureProvider` trims the key once and uses it everywhere.
