## A connection check must keep its settings through the committing continuation (2026-10-20 16:41, issues #214, #215, #216)

The current release, 1.16.12 at `9a0a671`, still reproduced the three
settings-pane failures. The issue's deferred real connection check reached
`good.example`, yet Enable committed `typo.example` after an edit while its
synthesis reply was held. The pane kept Disable after the real refusal
handler switched Premium off, and Fish's Manual IDs field became editable
after Test connection, a failed Enable or the account-only repaint.
The initial three reproductions gave the same five failures and three
passing controls in three consecutive runs, about 0.32 seconds each.

An additional direct-pref write proved why disabling inputs is not enough:
that write still changed the checked settings while the request was held.
Rejecting a changed configuration at the check boundary fixed both forms
in the experiment. Repainting on the enabled pref fixed the stale tier
button; reapplying the source restriction after a generic unlock fixed
all three Fish paths. These were local tests with controlled dependencies,
not a live Zotero pass.

The permanent seam is `test/ui/prefs-pane-state.test.ts`: the real
`onPaneLoad`, real connection check and real refusal handler, a small fake
document, synchronous Zotero-style pref observers, and no external
network. Before the implementation, it and the added provider-row cases
failed 19 assertions while 34 controls passed. The full suite after the
implementation passes 3,239 tests in 172 files. Both Standard and Premium
are covered for used-up and daily-limit refusals.

`provider-rows.ts` now owns the enabled-or-checking lock, including secret
reveal buttons. A check captures only its provider's effective settings
and blocked reason. Its return is evaluated in the caller's continuation,
immediately before acceptance: comparing before the last `await` would
leave one more microtask window in which a pref write could make a checked
result stale. A deterministic test writes in that window. Settings and
credentials in the snapshot remain inside the closure and are never
logged. A changed configuration gets a check-again message, not an
automatic retry. A stale restore failure cannot turn off a newer
configuration, and its summary cannot claim every provider was checked.

Enabled-pref observers repaint external changes. Own writes suppress only
those observers' duplicate callbacks; existing button and restore refreshes
keep their original behavior. External catalog and credits refreshes wait
one microtask and are coalesced, so a synchronous restore's switch writes
do not list a half-written section. Pane unload removes observers and
button listeners, and late checks no longer write settings.

Fish source and Model commands use the same lock as the provider rows.
Every generic unlock reapplies the Manual voices restriction through
`onUnlocked`; source observers cannot unlock a section that is still
checking. `test/ui/fish-provider-state.test.ts` runs the real three row
modules together and covers observer-driven repaints and synthetic
commands while the check is held. Saved manual IDs are not erased.

The four Biome error-level diagnostics in `prefs-pane.ts` are unchanged
baseline `forEach` callback-return lint findings; TypeScript passes.
No new configuration or preference is introduced. The user-facing cost is
that one provider's fields cannot be edited while its check runs; other
sections remain available. Live verification is pending on
`1.16.13-beta`, using the provider-controls, Zotero-tier and Fish-source
cases rather than the whole checklist.

## Verified live, and a reusable test must keep credentials it clears (2026-10-20 17:54, issues #214, #215, #216)

The first attempt stopped at a refused bridge connection, before any state
was touched. Once the owner started Zotero, the fresh pass ran on
11.0-beta.1+b551fb670 (Firefox 153). This is not a claim of live coverage on
Zotero 10. The installed XPI was byte-identical to the supplied build
(SHA-256 `fed53c1d0566b6074242378faeb70e184f66b7f735526c97798b83b6bb993a63`),
and startup reported 28/28 steps, none failed.

The local compatible stub held the synthesis reply. At 105 ms the entire
section and its two secret reveal buttons were locked while another off
provider stayed editable. An account notification did not unlock it.
Passing and failing replies settled as designed; direct address changes
made both Enable and Test connection report the check-again message,
without enabling the changed address. Closing Settings at 220 ms while a
reply was held left the switch off after release and produced no new
plugin error. A reopened pane reflected the prefs.

External writes to Standard and Premium repainted their labels in about
51 ms and removed the browser column within 157 ms. Both directions and
reopening Settings passed. Fish's empty-key checks failed before any
request; Manual IDs stayed disabled through both failures and an account
notification, became editable with Manual voices, and retained their text
when that switch went off again. No paid synthesis ran, no account changed,
and no readers were open or Players closed.

Review of the first retained kit found that its Compatible snapshot held
only the key's length before clearing it. The owner's key and headers were
empty, so no value was lost in this run, but that script could not safely
be reused with credentials. The tester retained full values privately
inside Zotero instead, refused snapshot overwrite, and added an executed
cleanup script. A nonempty synthetic credential was restored exactly,
including user-value presence; a deliberately abandoned held Enable was
settled as a failure, Settings closed before restoration, all six fields
verified, and the private snapshot discarded. Fish and tier scripts now
restore in `finally`; both revised versions ran successfully. The corrected
failure-poll script took 217 ms rather than its first revision's 12.7 s.

The stub itself is retained in the provider-controls kit. Reset settles
held replies before clearing them; stop closes sockets and timers. Five
otherwise unchanged live scripts gained loopback guards after their live
run. Those guards are tested without Zotero by
`test/live-kit-guards.test.ts`: all 22 allowed/rejected-address checks
pass before any profile, UI or network access. Their original behavior has
live evidence; their final guard additions have local evidence only.

Both passes restored values and user-value presence, WebDAV last (off,
no user value, `folder:false` before and after installation and cleanup).
Settings was closed, the stub stopped, and private snapshots discarded.
No recovery is owed. The enabled Compatible service already configured
in the owner's profile was offline and logged listing failures; those are
not a regression in these checks. The beta remains installed. The kits
and issue closing comments hold the detailed observations; no release was
made.

Final local checks: 3,261 tests in 173 files passed, including the 22 kit
address-guard checks. The first final-suite run had one failure in the
unchanged Fish catalog 20 ms deadline test
(`keeps cached manual voices after an official refresh consumes the deadline`).
Neither that test nor its provider implementation differs from the base.
The isolated 82-test Fish suite and the subsequent full suite passed
without code changes. This timing-sensitive failure is recorded rather
than silently counted as a first-run pass; its cause was not investigated
as part of the three settings fixes.
