## Andrew Natural HD is installed but absent from both Windows speech APIs (2026-11-05 11:24)

On Windows, Zotero 10.0.7 (Firefox 140) and OpenReader 1.17.0, the reported
voice is installed successfully, but enabling System voices does not offer
it. `Get-AppxPackage -Name MicrosoftWindows.Voice.en-US.AndrewHD.1`
reports `Status: Ok`. Its manifest declares a `windows.appExtension`
named `com.microsoft.voice.model.1`, with the display name
`Microsoft Andrew (Natural HD) - English (United States)`.

**Minimal reproduction:** call `diagnostics.systemProvider()` without a
voice argument, so nothing synthesizes or plays, and assert that a record's
name or id contains `Andrew`. Three calls returned `enabled: true`, nine
voices, no Andrew and no listing error, in 36, 50 and 21 ms. This already
fails below the Player's language and favorites filters.

**The deciding comparison:** a newly spawned PowerShell process ran the
actual `WINDOWS_DAEMON_SCRIPT`, with one framed `voices` request. Its raw
response also contained only three SAPI5 voices and six OneCore voices,
no Andrew, and `notes: []` (1,457 ms). The fresh process rules out a helper
retaining the pre-install list; inspecting its raw response rules out the
plugin's record conversion dropping Andrew. A separate fresh
`System.Speech` enumeration, including disabled voices, listed only the
three enabled Desktop voices, so the helper's enabled-only filter did not
hide it either.

The two enumeration boundaries are
`src/core/providers/system/daemon-script.win.ts:131` (`GetInstalledVoices`)
and `:140` (`SpeechSynthesizer.AllVoices`). Their records pass through
`src/core/providers/system/index.ts:94` and
`src/core/providers/system/voices.ts:70` to the diagnostic at
`src/index.ts:4312`. The installed bundle contains the same two API calls;
its SHA-256 is
`39b1e508c5f0e5c1ba7b1cddf2289d460f63bca2b2cb2a2daa6c867c4fc09aa2`.
No reader-internal behavior is needed to reproduce this absence.

**Conclusion:** this is an access-path support gap for the installed
Natural HD voice, not a failed installation, an Enable switch failure or
a hidden catalog row. On this machine neither Windows API used by the
provider exposes Andrew HD. This does not establish that every third-party
application is unable to use it. Offering its package name alone would not
supply synthesis; an additional integration would need to prove real audio
output before adding it to the catalog. No such integration or registry
change was attempted, and no production code or regression test was changed.
The diagnostic remains red; this investigation does not claim a fix.

Research probes remain in the gitignored scratch directory
`.tmp/zotero-dev/andrew-natural/`. No debug logging was added. The fresh
helper was terminated; the existing Zotero helper was not restarted.
WebDAV was isolated with its folder switch off and all observed transports
idle, then its original value and user-value flag were restored and
confirmed. No document, voice choice or volume was changed; Zotero was left
minimized. The only new console error was the initial probe using forward
slashes in an `IOUtils` Windows path; rerunning with a native path succeeded.

## Andrew HD word highlighting runs ahead because System.Speech mixes resampled byte counts with the voice's input rate (2026-11-05 15:33)

The affected voice is the exact local token
`sapi5/MicrosoftWindows.Voice.en-US.AndrewHD.1`, not an Online variant.
A read-only bridge check confirmed that the paused user Reading session
selected `system::sapi5/MicrosoftWindows.Voice.en-US.AndrewHD.1`.
The installed build is OpenReader 1.17.1-beta on Zotero 10.0.7.
Its XPI and bundle hashes still match the verified #241 build above.

**Reproduction:** run the actual exported Windows helper in a separate
PowerShell process, feed its real response through
`timestampsFromMarks`, and replay the resulting timestamps through the
Engine's real `wordAt`. Compare with the WAV's acoustic word intervals.
Nothing is played aloud. The single-sentence command is:

```sh
node --experimental-strip-types .tmp/zotero-dev/andrew-highlight/loop.mjs
```

Its text is `One, two, three, four, five.`. At 780 ms the audio is still
saying `two` (520-810 ms), but `wordAt` already selects `three`.
The fourth word begins acoustically at about 1,530 ms but is marked at
974 ms; the fifth begins at about 2,000 ms but is marked at
1,274-1,350 ms across runs. The verdict is FAIL, exit 1. David Desktop,
passed through the same helper/converter/Engine functions, passes:
its five marks differ from the acoustic onsets by at most 65 ms.

**Minimized request-level replay:**

```sh
node --experimental-strip-types .tmp/zotero-dev/andrew-highlight/loop.mjs "One. Two. Three."
```

Andrew's third mark is consistently 941 ms against an acoustic onset at
1,370 ms: 429 ms early. At 1,010 ms `wordAt` selects `Three` while
the audio is still saying `Two`. Repeated runs remain red; David's third
mark is 2,475 ms against 2,510 ms and its word selections pass. Removing
the third word yields PASS under the deliberately loose 300 ms drift
threshold and the spoken-word-selection assertions. The single-sentence
fixture above independently reproduces the same bug without crossing
sentence boundaries in the provider request.

The acoustic checker uses 10 ms RMS windows and joins internal silences
up to 120 ms. It is a coarse drift check, not forced alignment or a test
of subjective listening quality. It refuses a verdict as NOT TESTABLE
when the number of acoustic islands differs from the word count. Shorter
comma/semicolon fixtures encountered that limit and are not evidence of a
product failure. Small variations in individual event positions occur,
but neither the stable third-word drift nor the single-sentence verdict
depends on them.

**Ranked hypotheses and deciding experiment:** output-format/timeline
mismatch, inaccurate HD adapter boundaries, and System.Speech event-time
conversion. Change only the helper's requested WAV rate from 16,000 to
24,000 Hz. A diff of the two scratch helper scripts proves that the
`SpeechAudioFormatInfo` constructor's rate is the only changed line.

| Voice / output rate | Observed result |
| --- | --- |
| Andrew HD / 16 kHz, production helper | Progressive early marks; wrong spoken-word selections |
| Andrew HD / 24 kHz, scratch experiment | Three-word mark becomes 1,412 ms vs 1,370 ms; all five single-sentence selections pass, onset differences at most 92 ms in the retained final run |
| David Desktop / 16 kHz | Correct selections; no progressive drift |
| David Desktop / 24 kHz, same experiment | Marks run late; five-word final mark 4,822 ms vs 3,280 ms acoustic onset; the converter rejects the marks because they extend beyond the WAV |

The isolated Andrew-only experiment exits 0:

```sh
REPRO_VOICE=andrew OUTPUT_RATE=24000 node --experimental-strip-types .tmp/zotero-dev/andrew-highlight/loop.mjs
```

This is not a production fix: applying 24 kHz globally breaks David.
The unmodified original loop was rerun afterward and remains red.

**Source explanation:**

- The helper hard-codes 16 kHz in
  `src/core/providers/system/daemon-script.win.ts:97`, copies
  `SpeakProgress.AudioPosition` without correction at :98-100, and gives
  that format to `SetOutputToWaveFile` at :172.
- NaturalVoiceSAPIAdapter's
  [`GetOutputFormat`, lines 221-225](https://github.com/gexgd0419/NaturalVoiceSAPIAdapter/blob/88e5e72a00ae6f4fb32108173a464bcfea9838cc/NaturalVoiceSAPIAdapter/TTSEngine.cpp#L221-L225)
  explicitly returns 24 kHz / 16-bit / mono for embedded voices.
- The reference System.Speech implementation converts samples and adds
  the **output** byte count to `_bytesWritten`
  ([`AudioFileOut.cs:120-131`](https://github.com/dotnet/runtime/blob/7496f5e3859912052e96c65b80aa55aa100ec197/src/libraries/System.Speech/src/Internal/Synthesis/AudioFileOut.cs#L120-L131)),
  but `Duration` divides it by the **input** format's bytes per second
  ([lines 202-210](https://github.com/dotnet/runtime/blob/7496f5e3859912052e96c65b80aa55aa100ec197/src/libraries/System.Speech/src/Internal/Synthesis/AudioFileOut.cs#L202-L210)).
  Its event construction uses that duration
  ([`EngineSite.cs:298-300`](https://github.com/dotnet/runtime/blob/7496f5e3859912052e96c65b80aa55aa100ec197/src/libraries/System.Speech/src/Internal/Synthesis/EngineSite.cs#L298-L300));
  the SAPI event adapter also discards the original audio-stream offset
  ([`EngineSiteSapi.cs:30-41`](https://github.com/dotnet/runtime/blob/7496f5e3859912052e96c65b80aa55aa100ec197/src/libraries/System.Speech/src/Internal/Synthesis/EngineSiteSapi.cs#L30-L41)).
  This reference source explains the measured 16/24 time compression
  and its inverse for David; it is not a decompilation of the installed
  Framework assembly.
- `src/core/providers/system/protocol.ts:126` rejects marks past the
  audio's end but cannot detect marks compressed earlier into its valid
  range. `src/core/providers/system/index.ts:157` accepts those marks;
  `src/core/engine/words.ts:40` then selects exactly the word their bad
  times request. The fault precedes Highlight drawing and audio-device
  output latency.

The blanket comment that AudioPosition is always based on 16 kHz came
from measurements of the original Microsoft voices in #12. It does not
generalize to the adapter's 24 kHz embedded voice. #241 repaired voice
discovery; its positive mark count and in-bounds checks proved neither
acoustic synchronization nor correct word selection. This is a separate

**Recommendation:** keep the existing local voice integration and correct

estimated word timing are not a justified general fix. The specific

Temporarily using sentence highlighting avoids misleading word movement

## Per-voice PCM format negotiation keeps System word marks on the audio clock (2026-11-05 16:04, issue #242)

The fix keeps System.Speech for synthesis and asks the selected SAPI
engine for its default PCM format through the public
`ISpObjectWithToken` / `ISpTTSEngine.GetOutputFormat` interfaces.
The small original C# binding is compiled lazily in the existing helper;
the format query never calls Speak, installs a component, edits a token,
or accesses framework-private fields. Owned COM objects and the returned
CoTaskMem format are released. Only validated PCM formats that
SpeechAudioFormatInfo can represent are accepted.

The public VoiceInfo.SupportedAudioFormats collection is empty for
Andrew, David, Zira and Huihui on this machine. Querying the actual engine
instead returns 24 kHz / 16-bit / mono for local Andrew HD and
16 kHz / 16-bit / mono for the three Desktop voices. SpeakSapi requests
that same format, so System.Speech does not mix output byte counts with
another format's byte rate. Results, including failed queries, are cached
by the selected voice's token for this helper's lifetime; #241's queued
helper replacement also clears the cache.

If a format cannot be verified, synthesis keeps the old 16 kHz audio
fallback but withholds its untrusted word marks. An explicit timingNote
travels through the framed response, provider result and pane timestamp
check, rather than incorrectly claiming the engine produced no marks.
The existing whole-Segment fallback supplies sentence highlighting.
OneCore's real cue track, macOS, Engine speed/latency handling, character

## Andrew Online selection collides with the shorter Andrew name (2026-11-05 16:56)

On Windows, Zotero 10.0.7 and OpenReader 1.17.1-beta2, switching from
Microsoft Andrew to Microsoft Andrew Online reports that the previous
voice is kept. The installed XPI and bundle hashes match the #242 beta2
record above. This is a separate selection failure, not a recurrence of
its word-clock drift or #241's stale discovery.

**Minimal reproduction:** the actual exported Windows helper, in a fresh
PowerShell process with PATH removed, receives one `speak` request for
`sapi5/Edge-en-US-AndrewNeural`, with text `One.`. Two independent runs
fail in 848 and 875 ms with `SelectVoice`: `Cannot set voice. No matching
voice is installed or the voice was disabled.` The original
Andrew HD -> Andrew Online sequence also fails, after Andrew HD produces
27,646 bytes of WAV. Starting the old voice is therefore unnecessary.
The unattended research command is:

```sh
REPRO_VOICES='sapi5/Edge-en-US-AndrewNeural' node --experimental-strip-types .tmp/zotero-dev/andrew-online/loop.mjs
```

The exact Online token is listed and enabled. Native `SAPI.SpVoice`,
selecting that token directly, produces 33,886 bytes of WAV without
playback. `System.Speech.SelectVoice('Microsoft Andrew Online')` fails
outside Zotero too. Each name occurs only once, but the shorter local
name `Microsoft Andrew` is a space-delimited prefix of the requested
name. Microsoft AndrewMultilingual Online selects and synthesizes
successfully in the same independent probes.

**Deciding experiment:** change only eligibility of the local Andrew HD
candidate in the throwaway process, using the public
`InstalledVoice.Enabled` property. With that shorter candidate excluded,
`SelectVoice` returns the exact requested `Edge-en-US-AndrewNeural`
token. The same helper's Andrew HD -> Andrew Online sequence then passes,
producing 27,646 and 36,910 bytes of WAV. A diff confirms that this
process-local candidate exclusion is the only script change. It edits no
registry or Windows setting and is not an applied production fix.

The plugin first resolves the exact token to its name, then calls
`$s.SelectVoice($name)` at
`src/core/providers/system/daemon-script.win.ts:242-245`, losing the
selection's unique identity. The reference System.Speech implementation's
`VoiceSynthesis.MatchVoice` accepts space-delimited substring matches in
list order, while `SpeechSynthesizer.SelectVoice` subsequently requires
an exact name and throws on the shorter result
([matching](https://github.com/dotnet/runtime/blob/af3bd855514c4ea3151dcd63ae7290f1dc3f5e13/src/libraries/System.Speech/src/Internal/Synthesis/VoiceSynthesis.cs#L1151-L1181),
[validation](https://github.com/dotnet/runtime/blob/af3bd855514c4ea3151dcd63ae7290f1dc3f5e13/src/libraries/System.Speech/src/Synthesis/SpeechSynthesizer.cs#L35-L45)).
This is reference-source explanation, not decompilation of the installed
Framework assembly. The native public-API experiment confirms the failure
and its dependence on the shorter candidate on this machine.

Bypassing only #242's format query does not change the failure; selection
fails before that query. A repeated unmodified-helper run after the
experiment still fails. This rules out that new format query as the cause
of the deterministic Andrew Online selection error.

**Independent live-state complication:** the installed helper had already

**Recommendation:** preserve exact voice identity during System.Speech
selection, with a real-helper regression covering both conflicting names

## The shared anchor needs the whole boundary and candidate-ranking fix (2026-11-05 21:30, issue #234)

PR #244 was reviewed but not merged. Its simplified boundary check chose
UTF-16 offset 8 rather than 2 for `你好` in `前文你好后文。 你好。`, even with
stored prefix `前文` and suffix `后文`; both the existing plugin and
OpenReader's full fix chose 2. A rejected character substring could still
pass token or approximate matching (`第1章` in `第1章的故事`, or
`Volume One Chapter 1` against `Volume One Chapter 10`). Astral digits and
combining marks also escaped the simplified `charAt` check. These are host
observations, not Zotero runtime results.

The replacement matcher comes directly from Xujia Liu's OpenReader commit
[`18b37fbd846885a29d63963818cb9e57d3a50264`](https://github.com/xujialiu/OpenReader/commit/18b37fbd846885a29d63963818cb9e57d3a50264),
`src/core/document/anchor.ts`. Its contents from `type Token` to EOF compare
identically after the port; only the plugin's copy header and import path/order
are local. Neither PR #244's added implementation nor its added test was
used. The contributor was thanked, the gaps explained, and the takeover
announced in the PR before implementation. The upstream ADR 0008 supplies
the boundary/context rules; the plugin's shared format section 6.5 now
states them without changing any field or context length.

Every candidate is considered, but only the winner and its tie flag are
retained. Context scoring binary-searches token edges and checks the stored
context instead of scanning a whole block for each occurrence. In Node
22.23.2, a 238,889-character block with 10,000 contextual `Yes.` replies
resolved at the final offset 238,885 in 31, 30 and 20 ms on three runs of the
replacement. The reviewed partial port took about 1,806 ms on the same input;
these are illustrative host measurements, not timing thresholds or a live
Zotero performance claim.

The plugin's `sdt-anchor.best` additionally returns a tie when its winning
match is itself ambiguous. A locator names a block, not one occurrence.
Only the winner's ambiguity matters: a weaker ambiguous candidate must not
veto a stronger unique one, whichever is visited first. Existing
`resolveSharedItem` and `resumeFromShared` already refuse a returned tie;
no new fallback path or notice is necessary.

Two independently written regression files cover 39 cases. Before the fix,
29 failed and 10 passed; afterward the five targeted anchor/aligner/SDT files
passed all 101 tests. The complete suite passed 3,568 tests (12 skipped),
with typecheck and build passing. The Unicode, reflow, 64/65/100/10,000-copy,
stronger-winner and cross-text-node cases are host checks, not evidence of a
phone-to-Zotero run.

The test build is 1.17.1-beta4, chosen after checking origin/main and both
worktrees at beta3. The new `shared-anchor-integrity` case and its generated
EPUB specify the remaining real-resume and restoration evidence. This is a
pre-tester checkpoint; live acceptance, issue closure and PR closure are
still pending. Nothing has been pushed or released.
