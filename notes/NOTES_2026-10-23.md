## HTML display and Document analysis disagree about attachments and omitted body tags (2026-10-23 18:17, issue #228)

Research only, on macOS with Zotero 10.0.6 and Zotero-OpenReader 1.16.14.
The reporter's `cpp-memory-layout-editable.html` opens in the Reader and
renders its heading and 2,943 visible characters. A fresh close/open with a
bounded wait for the view took 451 ms. The reported inability to open the
page was not reproduced; whether the reporter means opening the page or
reading it aloud remains unconfirmed. No Zotero 9 comparison was run.

Two independently reproduced Zotero Document analysis barriers matter for
this file:

1. **An HTML Reader is not necessarily a snapshot attachment.**
   `xpcom/data/item.js:3530-3544` classifies every file attachment whose MIME
   type is `text/html` as Reader type `snapshot`, including an imported file.
   But `isSnapshotAttachment()` at `:2778-2780` requires link mode
   `LINK_MODE_IMPORTED_URL` (1); `importFromFile` creates
   `LINK_MODE_IMPORTED_FILE` (0). `xpcom/sdt.js:380-416` selects its processor
   with the narrower predicate and returns `unavailable` for mode 0 before
   parsing the file. For both the original file and a one-paragraph control,
   changing only the research attachment's link mode 0 → 1 → 0 produced
   unavailable → pack available → unavailable. File hashes stayed equal.
   This was a diagnostic mutation of disposable items, not a recommended
   migration of users' attachments.
2. **The snapshot parser requires a literal body element.** The supplied
   file starts a head but never explicitly opens a body. Gecko constructs a
   body for display. `resource/document-worker/worker.js:167714-167721`
   instead calls `parseXML(html, { xmlMode: false })`, looks up `body`, and
   returns `emptyStructure` if none was parsed. That empty result
   (`:167943-167961`) is a successful pack with no content, not a reported
   extraction error. With snapshot classification supplied, the original
   returned zero blocks; inserting only `<body>` before its first
   `<div class="wrap">` yielded 53 blocks and 1,977 extracted characters.
   A one-paragraph bodyless control also yielded zero; adding `<body>`
   yielded one block and 52 characters, while adding only `</head>` still
   yielded zero. CSS, scripts, Chinese text, and article filtering are not
   needed to reproduce this failure.

The two gates are sequential: adding the tag does not change attachment
classification, and changing classification does not supply the missing
tag. `resource/reader/reader.js:84062-84104` returns without Segmentation
when Document analysis is unavailable and clears the segments when the
result contains no sentences. Neither failure requires an OpenReader
Engine or provider call. The successful extraction does not establish that
all interactive content, hidden answers, or code samples will be read:
Zotero still applies its normal content filter afterward.

Research probes and fixture variants are retained in the gitignored
`.tmp/zotero-dev/issue-228/` directory, not in the live verification kit.
`repro.js` tests display; `analysis-loop.js` tests availability;
`link-mode-probe.js` runs the unchanged-file classification differential;
`body-loop.js` and `single-tag-loop.js` exercise the actual Zotero worker.
The body differential repeated with the same results in 36 ms. The shared
kit runner executes these files; no provider requests or audio playback
were needed. An early display probe checked `_internalReader` before async
initialization completed; the retained probe waits up to five seconds and
asserts the actual heading and visible text, rather than Reader.open's
return alone.

Cleanup removed all seven test attachments, their readers, and the test
Document voice preference. The WebDAV folder was already off; its value
and user-value status were snapshotted and restored exactly. The original
selected tab and window geometry were restored, and Zotero ended minimized
(`windowState: 2`). Volume and provider settings were untouched. Zotero
logged credential-decryption errors from its own sync notifier and blocked
the file's external Google Fonts stylesheet by CSP; these did not prevent
rendering or the successful extraction controls. No production code,
installed plugin, or Zotero source was changed.

## A temporary HTML adapter feeds Zotero a detached normalized copy (2026-10-23 19:31, issue #228)

The owner clarified the target as a page that displays but cannot be read
aloud, and approved targeted compatibility without converting attachments
or changing their files. The public plan is
[on #228](https://github.com/xujialiu/Zotero-OpenReader/issues/228#issuecomment-6363549855).
This entry records the implementation before live verification, not a
playback pass.

`src/read-aloud/html-document.ts` owns the temporary `Zotero.SDT.getPack`
wrapper. Native nonempty HTML and every non-HTML request stay native. Only
an unavailable local HTML attachment or an empty native HTML pack asks for
an inert browser-parsed source copy. `src/index.ts` supplies the Zotero
adapters: bounded UTF-8 reads, an MD5 over those exact bytes, a detached
`DOMParser` document's serialization, and the existing worker's queued
`getStructuredDocumentText` buffer request. No page script is evaluated and
no live Reader overlays enter that copy.

There is a second attachment gate in
`xpcom/pdfWorker/manager.js:652-658`, not just the one in `sdt.js`:
calling the public item-based worker method would still reject an imported
HTML file. Its `_enqueue` and `_query` methods (`:69-90`) accept a buffer,
content type, and source hash instead. The adapter uses that existing
protocol (`:677-685`; `resource/document-worker/worker.js:168788-168812`),
not a fork of the worker. The pack is inspected with Zotero's bundled
`structured-document-text.js` reader and `getTopLevelBlockCount`, so the
plugin does not invent pack layout or Document analysis.

Compatibility packs remain in memory: at most eight entries and 16 MB,
keyed by attachment ID and source hash. Concurrent calls for the same
source share preparation but receive separate buffers. A new source hash
does not join an older in-flight job. Source and normalized input each
have a 16 MB cap, preparation has a 30-second bound, failed jobs remain
retryable, and timed-out/disposed jobs cannot fill the cache afterward.
The wrapper restores its predecessor on shutdown only while it still owns
the slot. Idle HTML tabs with an earlier empty/failed analysis clear that
state after the old promise settles; active reading positions are not
reset. A preparation failure is logged and produces a localized notice
asking the user to close/reopen the document.

The initial native-forwarding test baseline failed 13 of 19 cases,
including unavailable imported HTML and zero-block snapshots. All 19
module tests now pass; the whole-startup test also drives the queued
adapter and proves unchanged attachment classification and restored
`getPack`. The first full suite passed 3,359 tests in 178 files. This is
not a same-realm substitute for live word/sentence alignment and Position
verification: `test/zotero-dev/cases/html-compatibility.md` states that gate.
The reporter's file remains local; the committed HTML fixtures are newly
authored, including a bodyless document with a script and a body-tag
mention inside a comment. No third-party example code was copied.
