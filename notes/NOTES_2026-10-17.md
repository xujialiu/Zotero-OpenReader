## A pick on an idle manager was restored over by the Document voice from before it (2026-10-17 20:28, issue #183)

Zotero persists a Player pick through `onSetVoice` into the reader's
`_setReadAloudVoice` (11.0-beta.1 `resource/reader/reader.js`
88538-88585; the 10.0.3 excerpt in `test/fixtures/engine/` is the same
flow). On an inactive manager that method does more than write the pref:
its branch at 88576-88583 runs `setLanguage(lang)`, then
`_syncPersistedVoicesToManager()`, then `activate()` when a voice is
selected, all inside the pick (`selectVoice`, `selectTier`, `setLanguage`
with `persist`). The memory sync runs a restore at two of those steps: the
`_syncPersistedVoicesToManager` wrapper's `apply()`, and the `activate`
hook's `resync`. Both read the document's voice from its record, and
`notePick` writes the pick into the record only once the pick has
returned. So both restores planned the voice from before the pick.

Measured in the issue's repro, instrumented, a Jenny pick with the
Document voice `local::af_aoede` unlisted: the entry got
`voice: azure::en-US-JennyNeural` from `_setReadAloudVoice`, then
`voice: local::af_aoede` from `apply` under the wrapper, with `planSync`
moving the `kokoro` key last in `tierVoices`. `applyPersistedVoices` then
missed the voice, and `_findFallbackVoice` (84902-84944) took the last
`tierVoices` key as its target tier, found it empty, widened to the whole
language and took the first voice of the region: Zotero's own tiers first
in the merged list, then the plugin's sorted by label. With Zotero Standard
listed, an Azure Entry pick ended active on `standard-ava`; without it, on
Aria. The activation guard let it through on `picking`, and `notePick`
saved the fallback as a manual Document voice. A language pick was lost
the same way (the manager went back to `en`).

The window opens only on an idle manager with the Player open. With an
available voice, Zotero's auto-activation (`_onReadAloudEngineStateChanged`)
has made the manager active before the user can pick, and an active
manager's `_setReadAloudVoice` runs no restore. The states that leave it
idle are the unavailable-voice guard (#146, #179) and no voice at all; with
no voice at all `documentChoice` is null and the restore plans no voice,
which is why the control case always kept the pick.

The memory sync now records, per manager (waived), a pick in flight: set
by the pick shadow outside its own moves (`applying`) and outside a
Handoff preview. While it runs and the manager is idle, `documentChoice`
answers the voice the manager has landed on, so both restores plan the
pick and leave Zotero's entry as `_setReadAloudVoice` wrote it. An active
manager keeps its session's voice. `test/read-aloud/document-voice-pick.test.ts`
runs Zotero's own manager with the real memory sync and provider tiers in
`index.ts`'s order.

## The memory sync's lifecycle hooks hid every later shadow of `activate` (2026-10-17 20:41, issue #189)

Since #146 the memory sync puts `activate`, `deactivate` and
`_createController` on each manager as own properties, and each hook ended
in the function it had read off the manager at attach: the prototype's.
The speech text settings shadow `activate` on the same prototype, and
attach after the memory sync at all three sites (`index.ts` 543 then 579,
799 then 812, and the startup steps at 2688 then 2711). Zotero calls
`activate` through the instance (11.0-beta.1 `reader.js` 88119 and
88582), so the own property won, and its captured function skipped the
shadow. The shadow's snapshot refresh never ran; the snapshot was filled
once, lazily, at the tab's first request, and kept for every later Reading
session in that tab. Swapping the two attach lines turns the issue's repro
green, which is how the order was confirmed as the cause.

The hooks now take the method as it stands at each call: an own one found
at attach, else `ownerOf(target, name)` at that moment, the shape
`attachMoveHook` already used for `_resolveVoice`. The general lesson: an
own-property hook that delegates to a function captured from the prototype
hides every prototype shadow added after it, in whatever order the modules
attach. `test/read-aloud/bracket-pairs.test.ts` now attaches the two
modules in `index.ts`'s order.

## Enable could not turn on a folder the server did not have yet (2026-10-17 22:15, issue #186)

Since #173 every upload waits for `webdav.enabled`, and Enable sets it
only after `client.check()` passes. The check is one PROPFIND Depth 0,
and a WebDAV server answers a collection it does not have with 404 (RFC
4918; Nextcloud's sabre/dav does). The 404 was thrown as `not-found`
with "It is created on the first upload", but the only MKCOL in `src/`
was the upload's fallback, behind the switch. So the README's own
examples, which end in a `zotero-openreader/` subfolder a first-time
user does not have, stopped at Enable from 1.16.7 on, and so did a
restore that turned such a folder on (#175). Profiles migrated with an
address already set, and folders that existed, never met it.

Enable and the restore check now send `check({ create: true })`, which
answers the 404 with one MKCOL: 201 or 405 passes, 409 (the parent is
missing) fails with "Check the address", and any other status fails with
it. Only the last segment is created. Test connection still creates
nothing. The regression test runs the real `initWebDAVRows` and
`createWebDAVClient` against a fake server that keeps RFC 4918's rules
(`test/ui/webdav-rows.test.ts`); the issue's own repro answered 404 to
every method and so could not go green under any fix that makes the
folder. Not checked live: whether Jianguoyun answers a missing folder
with 404, and whether it accepts MKCOL there.

## A stopped build kept arming retries from a run still in flight (2026-10-17 22:20, issue #220)

The shutdown bounds each final push at 8 s with `withTimeout`, a
`Promise.race` that cancels nothing, then calls `stop()`. A request to a
server that accepts and never answers is bounded at 15 s
(`WEBDAV_TIMEOUT_MS`), so it was still in flight at `stop()`, and when it
failed its handler armed a 60 s retry that nothing disarmed. Zotero keeps
a stopped plugin's scope and its timers alive (`plugins.js`
`_unloadScope` only deletes the scope; a disable drops nothing), so the
old build retried every 75 s or so. The settings auto-upload and the
settings sync transport now carry a `stopped` flag: `arm()` is a no-op
once it is set, the auto-upload's failure path no longer marks the change
pending, `changed()` is ignored, and the settings sync skips a trailing
run the single-flight had queued. The request itself still runs out its
own 15 s; aborting it would need a signal threaded from the shutdown
through every transport, and was left out. General lesson: a `stop()`
that only clears the current timer is not final while a run is in
flight — whatever that run arms when it ends outlives the instance.

## A change made during a slow backup upload waited for the next change (2026-10-17 22:21, issue #204)

The auto-upload clears `pending` before it awaits the upload, so a change
made during the upload sets it again and arms the 10 s quiet timer. When
that timer fired while the upload still ran, `run()` handed back the run
in flight and started nothing; the success path then looked at nothing,
so the change sat with `pending` true and no timer until another change
or a clean quit. The run's `finally` now starts the next upload when
`pending` is set and no timer is armed: the quiet period already ended
inside the upload. A change whose timer is still armed waits for it; a
failure keeps its retry. `single-flight.ts`, which the two transports
use, folds such a change into one trailing run by construction; the
auto-upload's own debounce did not.

## The shutdown's final pushes held it for one bound per file (2026-10-17 22:22, issue #219)

`shutdown()` awaited the auto-upload's flush, then the settings sync's
push, then the positions file's, then the Positions File's, each under
its own 8 s bound, so a folder that stops answering held an update or a
disable for 16 s at the default switches and 24 s with the settings sync
on (measured on fake timers by the test in `test/index.test.ts`). Nothing
needed the order: the four write different files, the transports already
run side by side on every poke, and none reads another's result. They now
start together under `Promise.allSettled`, each keeping its own bound and
its own log line, so one that throws is logged and the rest of the
teardown still runs; the store's drain and close still follow the two
positions pushes. A plugin update's gap (ADR 0007) now includes at most
one 8 s bound for them.

## Verified live on 1.16.12-beta: the WebDAV folder fixes, and timers that never fire after a re-enable (2026-10-17 23:22, issues #186, #204, #219, #220)

`zotero-tester` ran the build (xpi `4ce0983f…`, bundle `6721bf29…`) in
Zotero 11.0-beta.1 against the test WebDAV folder and a local stub on
`127.0.0.1`. The test server answered PROPFIND on a missing subfolder
with 404, MKCOL with 201 and MKCOL under a missing parent with 409, so
all three #186 lines read as written. Shutdown against a hanging stub
(#219): the three final GETs went out 2 ms apart, and the new build's
first request came 8433 ms after them, which bounds the old build's
shutdown. After a disable with the stub hanging (#220) the stopped build
sent nothing for 3 min 19 s. A change made 13 s into a PUT the stub held
for 14 s (#204) went up 14.03 s after the first PUT started, the moment
it was answered, and carried both changes.

Seen along the way, not caused by the branch and not yet compared with
1.16.11: after `addon.disable()` then `addon.enable()` in the same
session, the auto-upload's 10 s debounce never fired. `pending` stayed
`true` for over 10 minutes with no PUT and no error, while immediate
pokes still ran; the same probe on a fresh in-place install fired after
10.34 s. Zotero keeps a plugin's scope across a disable
(`plugins.js` `_loadScope` returns early when `scopes.has(addon.id)`),
so a timer host that stops scheduling there would hit every debounce and
sampler timer the re-enabled instance arms. Unverified beyond that one
module.
